# Automatic project verification

For non-web Node projects without package dependencies or workspaces, Miter runs the `*.test.mjs` files written or updated by the task. The existing isolated Node runner uses a read-only source copy and temporary test data. A changed snapshot or failed test returns to the task for repair. Project command profiles can run other suites with approval.

## Web apps

The host owns the completion gate. A generated app cannot disable checks, set lower scores or submit its own passing report. The bundled engineering skill documents `miter.quality.json`, including declarative `journeys`. They contain bounded clicks, form input, keyboard presses, reloads and DOM expectations; never JavaScript or shell commands. Every journey needs an action and an observable assertion. App authors must cover the main workflow, invalid data, persistence and keyboard dialog behavior where applicable.

Verification runs in order: implementation skill reads, connected component/source rules, JavaScript parsing, isolated domain tests, Chrome journeys, Lighthouse and unchanged-source checks. A failed finish returns concrete findings to the existing automatic repair loop. Retry and time budgets still apply; exhaustion or unavailable prerequisites is a failure, never completion. Earlier passing results cannot authorize a changed snapshot.

Chrome runs with its sandbox enabled in a new temporary profile, over a private debugging pipe. Miter serves immutable public assets. Apps with a `miter.backend.json` declaration also receive a same-origin API backed by the isolated project handler. A blocked proxy, exact snapshot-origin bypass and DNS restrictions prevent external or unrelated loopback requests. No user profile, cookies, extension privileges or host bindings are exposed. Browser processes, profiles, the local listener and disposable backend stores close on completion or cancellation. Audit jobs are serialized to avoid competing Miter runs distorting performance measurements.

For managed Vite and Next.js projects, Chrome exercises the real development server on desktop and mobile. Miter then builds and serves the production version of the same source for Lighthouse. When the build script runs `tsc` before `&& vite build`, the sandbox runs the installed TypeScript compiler first. Supported forms are plain `tsc`, `tsc -b`, `tsc --noEmit`, and `tsc -p tsconfig.json` (also spelled `--project` or `./tsconfig.json`). A type error returns to the task for repair before Lighthouse starts. Both servers use disposable installations and separate private origins. Each copy must match the original project fingerprint, which Miter checks again before accepting the result. An installation, startup or build failure returns to the task for repair.

Use `index.html` as the quality manifest entry for Vite. For Next.js, use the source page served at `/`, such as `app/page.tsx` or `src/pages/index.jsx`. The source check follows that page’s local imports and the applicable framework layouts. Domain tests remain explicit self-contained Node `.test.mjs` suites. The generated framework code and installed dependencies run together during the live browser checks.

Desktop and mobile journeys start with fresh browser storage. Static apps preserve that storage on reload. For backend apps, each journey starts with its own empty server store. A persistence journey must submit a new field value, reload and assert it in a visible element. The host clears browser storage on this reload, observes a successful API mutation and checks that a subsequent GET returns the asserted value. Lighthouse also starts with a fresh server store for each device. The runner checks console/runtime failures, missing responses, nonblank content, page overflow, clipped controls, keyboard focus and axe rules for WCAG 2 A/AA, 2.1 A/AA, 2.2 AA and best practices. It also checks the initial app at 320 CSS pixels. Screenshots record the exercised states. These checks sample declared journeys; they cannot prove all behavior or replace accessibility evaluation with assistive technology and users.

Form input replaces the previous value and verifies the exact result before continuing. Failed steps retain screenshots and bounded evidence about matching elements, visible invalid fields and control bounds. Overflow findings identify elements outside their containing blocks. Primary failures appear before repeated layout findings so the repair prompt retains the useful diagnosis. The field evidence and screenshots redact recognized password, contact, payment and one-time-code inputs.

During each browser journey, Miter checks for slogans and for short descriptions under headings that restate nearby controls or repeat an empty-state instruction. Findings quote the redundant line so the model can remove it while preserving the controls and help. Project conventions, the task request and applied user follow-ups can explicitly request a line or kind of copy. Later instructions can withdraw that request. The checks recognize common English patterns in the rendered states Chrome visits.

Once the Chrome journeys pass, Lighthouse runs its default navigation audits on desktop and mobile without category or audit exclusions. A failed journey returns its finding immediately, before Miter spends time building a production copy or measuring scores for a snapshot that needs repair. Every scored category must reach 100; the pinned version includes performance, accessibility, best practices, SEO and agentic browsing. Legitimately unscored/not-applicable audits remain recorded. Manual checks and informational diagnostics do not become fabricated passes. Scores describe the audited local page under Lighthouse’s device and throttling settings. The browser report records which journeys verified backend persistence on each device. WCAG conformance and deployed performance require separate evaluation.

A failed Lighthouse audit includes its first affected item in the repair message before the general audit description. For manifest errors this includes the reported issue and the affected resource. Full Lighthouse JSON/HTML reports and screenshots live in the host data directory under `quality-reports`. Retention keeps the latest completed runs; active runs are protected. The gate fingerprints the source, public assets and declared backend modules with SHA-256. Supported backend handlers use local modules and Node built-ins. Other servers and external services require a separate environment. Prerequisite inspection does not run supplied code or launch Chrome.

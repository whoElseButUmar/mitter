# Built-in task defaults

Fresh task prompts include the bundled Caveman and No AI Slop writing rules and Ponytail’s guidance for coding and code review. There is no dependency on a user's Codex installation, network access, or model download. Local tasks, chat bootstrap/review/fix/next prompts, follow-ups, and repair prompts share the same registry. AI draft rewrites receive the writing rules without the app-building instructions.

`../task-skills.ts` owns the validated, immutable catalog and renders the prompt block. The writing rules and compact engineering/design rules are always included. A read-only `{"type":"skill","name":"app-design"}` action retrieves the full UI guidance and exact CSS reference before UI implementation; the other built-in names work too. This keeps detailed UI references out of backend-only tasks. Skill reads cannot access arbitrary paths, install packages, issue edit references, or modify project files.

`writing.ts` adapts the two installed writing skills to Miter's strict JSON transport. The original snapshots and their licenses ship in `apps/extension/public/skills/`. `engineering.ts` covers readable code, domain boundaries, backend validation and authorization, failure recovery, and evidence-based verification.

`app-design.ts` provides the shared CSS foundation and component rules. Generated apps should use one set of theme tokens and reusable controls for inputs, selects, popovers, date pickers, dialogs, and scroll areas. The reference colors are replaceable defaults, not a universal brand. Existing projects map the foundation to their established components. A backend-only change does not acquire UI work.

Copy the dependency-free date, time, dialog and confirmation controls with `{"type":"write","path":"components.mjs","asset":"components.mjs","base":"missing"}`. Use `"asset":"foundation.css"` to copy the stylesheet. Both writes use the destination file’s normal version precondition and journal. Miter checks the expanded reply against its byte budget. A separate skill read can inspect either asset. The modal shell clips its rounded corners while only the body scrolls; header and footer stay visible. Scrollbars are thin and themed, with native keyboard/wheel/touch behavior and high-contrast fallbacks. Use appropriate accessible primitives from an existing stack instead when they meet the same contract. A date range or preset belongs only where the requested workflow needs it. Shadcn is an interaction and composition reference, not a required dependency or an unchanged visual template.

## Design decisions

- Keep visible controls intentionally styled. Preserve semantic HTML, browser editing, autofill, validation, zoom, and accessibility settings. Use a tested custom widget where a browser popup cannot meet the design across supported browsers.
- Use one CSS `:focus-visible` outline, not a permanent focus glow or JavaScript tracking the last input device. Text inputs may match `:focus-visible` after pointer focus; this is the browser's accessibility behavior. Forced colors may override the app theme.
- Inset select indicators with logical padding; give the value room to wrap or truncate predictably. Do not pin a chevron against the edge.
- Keep native scrolling and a visible, usable scrollbar. Never hide overflow to disguise a broken layout or intercept wheel/touch scrolling for decoration.
- Start with a short product brief covering audience, primary task, realistic content, density, brand and constraints. Use it to choose hierarchy and layout. Group related content through proximity and alignment; use cards and elevation when they explain a relationship or interaction. Check long content and narrow containers, not only viewport width.
- Keep copy that identifies content, explains an action, reports a state or helps someone correct a mistake. A title can stand alone. Taglines, decorative text above headings, promotional subtitles and footer slogans require an explicit request for that copy. A visual style or audience description alone does not request it.
- Give icons, accents, badges and status colors a meaning. Counts, metrics, connectivity and save messages must reflect real state. Label demonstration data. Remove decorative dots, repeated arrows and helper text that repeats a label.
- Review repeated hero/card layouts, tiny secondary text, excessive uppercase labels, arbitrary gradients and blanket animation in context. Mandatory cream/green, editorial serif or black/neon themes are replacement templates, not universal improvements. Preserve user branding; do not ban fonts, palettes or icon libraries. “AI-looking” is a design critique, not proof of authorship.
- Target WCAG 2.2 AA and exercise the supported populated, empty, loading, invalid and recovery states. Check keyboard navigation, unobscured focus, contrast, names, reflow, usable targets, menus, dialogs, scrolling and persistence where relevant. Rendered checks can find observable failures; they cannot decide whether a layout fits its audience or establish full accessibility conformance.

Changed web apps also have executable completion gates. The host requires the two implementation skills to have been read in the current run, validates `miter.quality.json`, follows linked/imported styles and components, checks native picker/dialog and scroll/focus source rules, parses JavaScript and executes the declared domain tests against a copied source snapshot. It also runs the declared browser journeys and Lighthouse at desktop and mobile sizes. Every default scored Lighthouse category must reach 100/100. A failing gate returns findings for automatic repair and rerun within the task's run budget; a file-existence check cannot bypass it. There is no manifest opt-out or lower threshold. The evidence records the checked source and check scope; report blocked or unfinished checks honestly.

The manifest keeps `version: 1`, `entry`, `styles`, `components` and `tests`, and requires `journeys`. The engineering skill includes a complete example. Supply 1–6 distinctly named journeys with 2–32 steps each, including an action and an observable expectation. Cover the main workflow, invalid input, persistence and keyboard dialog behavior when present. Each journey starts with fresh storage; `reload` retains storage within that journey. Use stable CSS selectors for the real controls, including custom components.

Steps are `click` with `selector`, `fill` with `selector` and `value`, `press` with `key`, `reload`, or `expect` with `selector` and an assertion. Expectations support `visible`, substring `text`, exact `value`, `count` and `focused`. Allowed keys are `Tab`, `Shift+Tab`, `Enter`, `Escape`, `Space`, the four arrow keys, `Home` and `End`. These are declarative browser actions, not project scripts. Keep assertions tied to user outcomes so broken behavior fails the journey.

For a Vite app with a Node backend, the engineering skill supplies the version-checked `vite-api.mjs` write asset. Its `viteApi(handle, isPage)` plugin serves the project's JSON API in both Vite development and production preview. The app identifies its own client routes in `isPage`, so a deep link can load the UI while a missing asset returns 404. The adapter passes the project storage directory to the declared backend handler. SQLite databases placed in that directory survive managed server restarts. Standalone Node servers can reuse `apiMiddleware(handle)` and set `APP_DATA_DIR`.

For projects declaring `miter.backend.json`, the browser gate checks that a submitted value survives a reload and comes back from the API on both viewports. Each journey uses fresh server storage.

The isolated test runner currently requires macOS and Node 26+. It verifies the OS sandbox before running tests, denies network and child processes, keeps source read-only and writes only to temporary test data. Unsupported hosts fail closed. Existing registered commands retain their approval requirements. Source/domain checks, browser journeys and Lighthouse have separate scopes: recorded journeys and viewports are not exhaustive browser or backend integration coverage. A perfect score does not prove visual quality or WCAG conformance. Keep requested behavior intact when fixing audits; never hide errors, detect an audit user agent or add fake metadata/tools to manufacture a pass. Writing skills remain always-injected guidance, not a machine proof of human authorship.

Existing sent prompts and their receipts remain byte-for-byte intact. Existing files change only when a task edits them; fresh prompts pick up the new defaults after updating Miter. Third-party skill snapshots remain unchanged.

## Research checked on 12 November 2026

- [MDN: `:focus-visible`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:focus-visible): browser focus heuristics and accessible CSS focus styling.
- [WAI-ARIA combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) and [date picker example](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/): labels, keyboard interaction and focus management. Examples need testing in the target browser/assistive technology; they are not blanket compatibility guarantees.
- [shadcn Date Picker](https://ui.shadcn.com/docs/components/radix/date-picker) and [Scroll Area](https://ui.shadcn.com/docs/components/radix/scroll-area): composed calendars, ranges, and custom appearance around native scrolling.
- [Anthropic: Improving frontend design through Skills](https://claude.com/resources/articles/improving-frontend-design-through-skills): deliberate design direction reduces repeated template choices. Miter keeps the user's existing stack, offline constraints and chosen style rather than adopting that article's sample font or network requirements.
- [InterfaceKit: What makes a website look AI-generated?](https://blog.interfacekit.io/what-makes-a-website-look-ai-generated): a practitioner critique of interchangeable content, incomplete states and inconsistent rules; not an authorship test.
- [NN/G: UX-context design](https://www.nngroup.com/articles/ux-context-design/) and [chunking](https://www.nngroup.com/articles/chunking/): product context and meaningful grouping guide composition. [Its flat-UI study](https://www.nngroup.com/articles/flat-ui-less-attention-cause-uncertainty/) supports recognizable interaction cues, not shadows on every element.
- [Google Design: sparkle icon research](https://design.google/library/ai-sparkle-icon-research-pozos-schmidt): icon interpretation depends on product context and labels. An icon does not reveal who made an interface.
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/): accessibility requirements include behavior and states beyond what a single automated page audit can test.
- Google Chrome's `modern-web-guidance`: retrieved `forms`, `browser-ui-theming`, `branded-select-styling` and `natural-interactions`. Customizable select support varies; the default requires a working accessible fallback for the app's supported browsers.
